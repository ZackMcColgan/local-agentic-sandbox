## Executive Summary

The Nov 21–22, 2026 full-board trial surfaced five concrete runtime failures (Exhibits E1–E5). First-hand inspection of the checked-in runtime at `6402579` proves that every exhibit stems from specific, reproducible mechanisms in the turn engine, thread store, stream writer, and board drain:

1. **Orphaned & failed board turns are unconditionally parked instead of recovered (E1, E4).** `BoardOrchestrator.drain()` sets an item to `working` before `threadLink` is persisted (`boardOrchestrator.ts:560`), and `createProductionWorkingItemLivenessCheck` marks any missing-link or reconciled-`stopped` thread `"orphaned"`, which `BoardOrchestrator.drain()` unconditionally parks at `needs-attention` with zero retry or requeue branch (`boardOrchestrator.ts:525-541`). Meanwhile, the `"Auto-resume attempt 1/2"` supervisor (`inAppSupervisor.ts:113-182`) never fires for board-drain threads (they lack `taskId`), cannot fire after a pod restart (`sweepStalledThreads` calls `getThread` -> `reconcileThread` first, flipping `active` -> `stopped`), and strips all host tools whenever it does fire on a `taskId` thread (`roundLoop.ts:383-389`).
2. **Silent mid-turn termination has multiple active triggers with hidden or generic errors (E1).** Beyond pod restarts/OOMKills, an active board turn can lose its outcome or terminate mid-work via: (a) `sseWriter` aborting `stream.readable` on a 2-second `writer timeout` while `runChatTurn` keeps running detached (`turnEngine.ts:102-127`, `productionDrain.ts:133,267-273`), (b) `jobChunkingEnabled` (default `true`) cutting off turns at 25 rounds / 45m with `[[CHUNK_COMPLETE]]` or crashing `bankGitWork` in `/app` while `productionDrain.ts` never implements the `chunk-complete` return contract (`roundLoop.ts:673-694`, `productionDrain.ts:219-226`), (c) `sweepStalledThreads` stamping a live thread `stopped` on disk without aborting `runChatTurn` (`threadStore.ts:511-559`, `inAppSupervisor.ts:79-108`), (d) `hasArtifactCreationIntent` + a single web tool call breaking out of the round loop immediately (`roundLoop.ts:1798-1800`), (e) clean EOF / empty tool-less round from the inference engine (`provider.ts:697,891`, `roundLoop.ts:1277`), and (f) unregistered-tool throw when a transient host-runner probe blip withholds host tools (`roundLoop.ts:386-389,1518`).
3. **"Round 55 · STALLED · No heartbeat for 1730s" is caused by two disconnected heartbeat/stall systems (E2).** On the client, `ChatStream.tsx:309-311` only updates `lastActivityAtMs` when `isLoading` is `true` — which is always `false` when observing a board-drain turn polled via `GET /api/threads/[id]` (`app/page.tsx:492-522`) — and `ChatStream.tsx:1019-1261` ignores server `{ type: "ping" }` events completely. On the server, `touchActiveTurn` is called only once at the very end of a round (`roundLoop.ts:1770`, redundant with `streamSnapshot.maybeWrite(..., { force: true })` at line 1757), leaving multi-minute uninterruptible spans (`host_run_powershell` up to 605s exceeding `STALL_WINDOW_MS = 600s`, `LlamaCppProvider.streamChat` buffering `delta.tool_calls` with zero yields until EOF, synchronous `bankGitWork` `git push` with no timeout, and 300s hybrid compaction) with zero record heartbeats.
4. **Output tokens are overwritten per round (`717` instead of cumulative total) and `rounds` is off by 1 (`307` vs `308`) (E3).** `roundLoop.ts` already accumulates `cumulativeOutputTokens` (`roundLoop.ts:646,1037-1039`) and writes it to mid-turn snapshots (`roundLoop.ts:1765`), then discards it on final settle at `roundLoop.ts:2102-2103` in favor of `turnState.turnOutputTokens` (the last round's value only). That bug also corrupts settled `tok/s` (`turnSpeed.ts:27-44,165`). Meanwhile, `round` only increments on continuing iterations (`roundLoop.ts:1292`), never on terminal `break` rounds (`roundLoop.ts:1277`), and `turnStartMs` (`roundLoop.ts:661`) still excludes queue wait, MCP connect, Oracle lookup, and turn-start compaction.
5. **Marathon context economics (`11.69M` prompt tokens, `93.7K` peak, `1` compaction) reflect estimator undercounting, un-elided prompt floors, and dead mid-turn hybrid compaction (E5).** `estimateTokens` (`chars / 4`) undercounts code/JSON BPE tokens and omits tool schemas, allowing real prompt tokens to reach `93.7K` before `estimateTokens` crosses `85,000`. Micro-elision keeps context in a 40K–84K plateau across hundreds of rounds while small tool results (`< 2000` chars), all assistant `tool_calls` arguments, and uncapped file reads accumulate. Even when `COMPACTION_STRATEGY=hybrid` is enabled, `compactThreadIncrementalHybrid` returns `noop: "insufficient_messages"` mid-turn on any single-turn marathon (`threadStore.ts:1585`), and Rung (a) extraction compaction evicts the sole `user` brief into a 2,000-char excerpt inside an `assistant` message (`conversationCompaction.ts:487,622-636`).

## Exhibit E1 — Turns End Without an Outcome

> Observed failure: Board items `#57`, `#61`, `#62` each ran a job thread (`#61` = `thread-1795369897556-1vto`, `#62` = `thread-1795376706393-3fmr`) whose turn stopped without a final summary, PR, or commit, and the drain stamped the item `needs-attention`.

### End-to-End Turn Lifecycle Map

1. **Board dispatch (`web-ui/lib/board/boardOrchestrator.ts:553-568`, `web-ui/lib/board/productionDrain.ts:186-216`):**
   - `BoardOrchestrator.drain()` marks the board item `status: "working"` (`boardOrchestrator.ts:560`) **without** `threadLink`.

2. **Chat route entry & serialization (`web-ui/app/api/chat/route.ts:86-484`, `web-ui/lib/chatTurnGate.ts:46-98`):**
   - `POST` adds `activeThreadId` to `activeExecutionSet` (`route.ts:210`), calls `markTurnActive(activeThreadId)` (`route.ts:213`), and seeds an empty streaming assistant placeholder (`content: "", status: "streaming"`) via `threadStore.addMessage` (`route.ts:218-226`), setting `thread.status = "active"` on disk (`threadStore.ts:1237-1238`).
   - Registers `turnAbortController` (`route.ts:378`) with an `abort` listener calling `persistAssistantOnAbort()` (`route.ts:381-384`), creates `sseWriter = createSseEventWriter(...)` (`route.ts:386-390`), enqueues into module-singleton `chatJobQueue` via `serializeTurn` (`route.ts:445-476`), and immediately returns `new Response(stream.readable)`.
   - `serializeTurn` creates a per-job worktree (`chatTurnGate.ts:69`, errors silently ignored -> `worktree = null`), acquires the single engine slot in `PrioritySlotScheduler.runWithSlot` at `SlotPriority.P0_OWNER` (`chatTurnGate.ts:77-86`, `route.ts:454`), and runs `runChatTurn(deps, job, worktree)`.
3. **Round loop & settle/persist (`web-ui/lib/chat/roundLoop.ts:222-2330`):**
   - Connects MCP sandbox & browser clients (`roundLoop.ts:349-367`), probes host runner (`roundLoop.ts:386`), runs turn-start compaction (`roundLoop.ts:441-467`), enters `while (true)` (`roundLoop.ts:671`), streams LLM chunks, executes tool calls, forces a snapshot + `touchActiveTurn` at round end (`roundLoop.ts:1757-1771`).

### Separating Hypotheses for `#57`, `#61`, `#62`

Because the thread JSON files for `thread-1795369897556-1vto` (#61) and `thread-1795376706393-3fmr` (#62) live on the cluster PVC rather than in git, the code separates the root causes cleanly by inspecting three fields on each thread/board record:

- **Board `parkedReason === "Job thread ended without an outcome (possible restart)"` + message contains `⚠️ [Turn incomplete: Server restarted or turn interrupted.]` (or board item has no `threadLink`):** Proves **Path 1 (pod restart / OOMKill)** -> `reconcileThread` -> orphan recovery.
- **Board `parkedReason === "writer timeout"` while the thread JSON continued accumulating rounds/traces after `boardItem.updatedAt`:** Proves **Path 2 (`sseWriter` 2s timeout aborting `stream.readable`)**.
- **Board `parkedReason === "Job turn failed for thread <id> (HTTP 200)"`:** Proves **Path 3, 4, 6, 7, or 10** — separated by checking the last assistant message's `status` (`"incomplete"` vs `"error"`), `roundFinishReasons`, and trailing marker (`Turn stalled:`, `EMPTY_SYNTHESIS_STAMP`, `[[CHUNK_COMPLETE]]`, `TURN_SIZE_LIMIT_MARKER`, `TURN_TIMEOUT_MARKER`, or `⚠️ [Turn error:`). Specifically, if the message has `status: "incomplete"` and `roundFinishReasons` ends in `"stop"` with `EMPTY_SYNTHESIS_STAMP` (or no error marker), **Path 4 (clean engine EOF / empty round -> failed synthesis)** or **Path 3 (`sweepStalledThreads` stall stamp)** occurred.

### Blast Radius & Proposed Fix Shape (E1)

- **Blast radius:** Every unattended board job and interactive multi-round turn.
- **Proposed fix shape:**
  - `web-ui/lib/chat/turnEngine.ts`: Do **not** call `writer.abort()` on `writer timeout` when the caller is an in-process consumer, or increase `writerTimeoutMs` for in-process drain calls and decouple drain completion from SSE backpressure (e.g. await `serializeTurn`'s `settled` promise or poll `ThreadStore` instead of relying solely on `stream.readable`).
  - `web-ui/lib/board/productionDrain.ts`: Surface the actual last assistant message error/marker text when `settled.status === "stopped" | "failed"`, check `[[CHUNK_COMPLETE]]` and return `{ status: "chunk-complete", threadId, handoff }`, and wire `classifyJobSummary` _before_ rejecting `stopped` threads.

  - `web-ui/lib/chat/roundLoop.ts`: Guard `isArtifactRequest && traces.some(isWebResearchTool)` (`roundLoop.ts:1798`) so coding/repo turns with host/workspace tools do not break after a single web search; scope `MAX_STREAMED_CONTENT_CHARS` (`roundLoop.ts:1007`) to per-round content (`fullRoundContent.length`), not cumulative turn narration; persist an error/incomplete message before returning on `approvalContinuationId` failure (`roundLoop.ts:521-534`).

### Exact Root Cause of `"Round 55 · STALLED · No heartbeat for 1730s"`

Two defects combine to produce the exact observed symptom:

1. **Client-side UI Silence Bug (direct cause of the 1730s banner on a live observed board turn):**
   - When the user opens a running board job thread in the UI, `app/page.tsx:490-522` polls `GET /api/threads/${selectedThreadId}` every `STREAM_POLL_INTERVAL_MS` (`1500ms`) and updates `messages` while `lastAssistant.status === "streaming"`.
   - Because the browser did **not** start the `POST /api/chat` request, `ChatStream.tsx:278` has `isLoading === false`.
   - `ChatStream.tsx:2324-2334` passes `isStreaming={Boolean(isLoading || lastAssistant?.status === "streaming")}` (which is **`true`**) and `lastActivityAtMs={lastActivityAtMs}` to `NowLineBar` (and `ChatMessageItem` / `LiveActivityHeader` at line 2456).
   - Meanwhile, `ChatStream.tsx:309-311` is:
     ```ts
     useEffect(() => {
       if (isLoading) setLastActivityAtMs(Date.now());
     }, [isLoading, streamStatus, messages, liveTurnTraces]);
     ```
   - Because `if (isLoading)` is **`false`**, `setLastActivityAtMs` is **never called once after mount**, even as rounds 1 through 55 stream in via polling! `lastActivityAtMs` stays pinned to the initial `useState(() => Date.now())` timestamp (`ChatStream.tsx:301`). After 1730 seconds (~28m 50s) with the tab open, `freshnessFor(lastActivityAtMs, nowMs)` computes `secondsAgo = 1730 > 45` (`liveActivity.ts:23-28`) and renders `STALLED · No heartbeat for 1730s` (`LiveActivityHeader.tsx:109` / `NowLineBar.tsx:55` via `turnSpeed.ts:179`).
   - Even on locally initiated SSE turns (`isLoading === true`), `ChatStream.tsx:1019-1261` has **no handler for `event.type === "ping"`**, so any tool execution or LLM prefill silent for `> 45s` flips the UI banner to `STALLED` despite `turnEngine.ts:134-142` emitting a `ping` every 10s!

2. **Server-side Heartbeat Starvation During Long Uninterruptible Spans:**
   - The server stall detector (`inAppSupervisor.ts:8,51-73` and `liveness.ts:5,48-58`) checks `now - Date.parse(thread.updatedAt) > STALL_WINDOW_MS (600_000ms = 10m)`.
   - `roundLoop.ts` **never** runs a periodic `touchActiveTurn` timer during a turn and **never** calls `touchActiveTurn` before or during tool calls, compaction, or queue waits.

### Why `"Auto-resume attempt 1/2"` Exists Yet Always Loses

1. **Board-drain threads have no `taskId`:** `productionDrain.ts:208-211` calls `threadStore.createThread({ title, initialPrompt: brief })` without `taskId`. When `superviseStalledThread` inspects any board-drain thread, `inAppSupervisor.ts:142` (`if (!thread.taskId) return { action: "ended_only" }`) treats it as an interactive user turn and never resumes it.
2. **Pod restarts defeat `sweepStalledThreads` even for `taskId` threads:** `sweepStalledThreads` (`threadStore.ts:521`) calls `this.getThread(s.id)`, which calls `this.reconcileThread(thread)` (`threadStore.ts:1006`). After a restart, `!isLive` causes `reconcileThread` (`threadStore.ts:589-640`) to flip `thread.status` from `"active"` to `"stopped"` and `msg.status` to `"incomplete"` _before_ `superviseStalledThread` runs — so `detectStalledTurn` sees `isTurnStreaming(thread) === false` (`inAppSupervisor.ts:42-45`) and returns `"not_stalled"`! Auto-resume can therefore only trigger on a `taskId` thread that stalls >10m _in the same live process_ (or has `status === "running"`, which `reconcileThread` at line 589 misses).
3. **When `"Auto-resume attempt 1/2"` DOES fire on a `taskId` thread, four bugs make it lose:**
   - **Host tools stripped (`roundLoop.ts:383-389`):** Because the fresh thread carries `taskId: jobId` (`threadStore.ts:532`), `isProhibitedContext = Boolean(threadData?.isSubagent || threadData?.isScheduled || threadData?.taskId)` evaluates to **`true`**, withholding ALL host tools (`host_run_powershell`, `host_read_file`, `host_write_file`, `host_replace_string`, unattended git). The re-grounding brief instructs the model to run `git log` and read the runlog, but the model has no host tools to reach the host repo!
   - **Old stalled turn never aborted:** `superviseStalledThread` never calls `abortActiveTurn(thread.id)`, so the stuck original turn can remain in `activeExecutionSet` / `JobQueue` / `PrioritySlotScheduler`, blocking the resumed turn behind it.
   - **Unread SSE response body (`threadStore.ts:1025-1052`):** `dispatchSupervisorTurn` calls `fetch("http://127.0.0.1:3000/api/chat")` and on `res.ok` never consumes `res.body`, causing `sseWriter` to hit its 2s `writer timeout` immediately.
   - **Board item never updated:** `superviseStalledThread` knows nothing about `BoardStore` — the board item stays parked or linked to the old thread.

### Blast Radius & Proposed Fix Shape (E4)

- **Blast radius:** Every pod restart (including self-deploy rollouts) or transient stall permanently parks in-flight board items at `needs-attention` requiring manual owner intervention; every `inAppSupervisor` auto-resume on host jobs is guaranteed to lack host tools and fail.

Add bounded orphan/restart recovery in `BoardOrchestrator.drain()` (`boardOrchestrator.ts:525-541`): track `autoResumeCount` (and `handoff`) persistently on `BoardItem` in `boardStore.ts`; on `"orphaned"` (when the thread did not already open a PR/commit), if `autoResumeCount < MAX_AUTO_RESUMES (2)` re-queue to `queued` with incremented `autoResumeCount` and a re-grounding handoff brief instead of parking immediately; only park at `needs-attention` once the retry budget is exhausted. If the thread actually settled `completed`, inspect its outcome instead of classifying `"completed"` as `"orphaned"` (`productionDrain.ts:67`).
    3. Wire `chunk-complete` detection in `createProductionIssueAndWait` and persist `handoff` in `BoardStore.update()`.
  - `web-ui/lib/threads/threadStore.ts` + `web-ui/lib/threads/inAppSupervisor.ts`:
    1. In `sweepStalledThreads`, read raw thread JSON (or pass a `skipReconcile` flag) so restart-interrupted threads are evaluated by the supervisor before `reconcileThread` strips their `streaming` state, and call `abortActiveTurn(thread.id)` before dispatching a resume.
    2. Distinguish board-job threads from legacy Milestone-Task threads (`isProhibitedContext` in `roundLoop.ts:383`) or route board recovery exclusively through `BoardOrchestrator` so the two supervisors never fight over the same job.
  - **Proving tests:**
    1. Unit test in `web-ui/tests/boardOrchestrator.test.ts`: restart-orphaned `working` item with `autoResumeCount: 0` is requeued (`status: "queued"`, `autoResumeCount: 1`) on first recovery, requeued on second, and parked at `needs-attention` only on third; `threadLink` is persisted before `issueAndWait` resolves.

## Exhibit E5 — Context Economics of Marathon Turns

> Observed failure: 308 rounds re-sending accumulated context -> `11,691,655` prompt tokens total (~37,960 avg/round), last round `59K`, peak `93.7K`, exactly `1` compaction.

### Designed Thresholds vs. Observed Reality

The configured constants across `web-ui/lib/modelLimits.ts` and `web-ui/lib/contextBudget.ts` are:

- `DEFAULT_CONTEXT_WINDOW_TOKENS = 131_072` (`contextBudget.ts:15`)
- `CHAT_CONTEXT_BUDGET_TOKENS = 100_000` (`contextBudget.ts:14`)
- `ROUND_MAX_TOKENS = 16_384` (`modelLimits.ts:27`, applied as `num_predict` on every round via `computeModelOptions` -> `resolveRoundModelOptions`)
- `COMPACTION_THRESHOLD_RATIO = 0.85` -> **`85,000` estimated tokens** (`modelLimits.ts:30`, `contextBudget.ts:901`)
- `HYBRID_ESCALATION_RATIO = 0.65` -> **`65,000` estimated tokens post-extraction** (`modelLimits.ts:34`, `conversationCompaction.ts:36,308-309`)
- `MICRO_ELISION_RECENT_WINDOW = 5`, `MICRO_ELISION_MIN_RESULT_CHARS = 2000` (`microElision.ts:26,32`)
- `TOOL_ROUND_BACKSTOP = 1000` (`contextBudget.ts:36`)

**Verdict: This behavior is the literal mechanical consequence of the current thresholds and estimator — NOT a healthy design for marathon turns — and reveals five concrete defects where per-round prompt growth outruns compaction:**

1. **Why peak prompt tokens reached `93.7K` despite an `85K` trigger (`contextBudget.ts:227-262,880-917`):**
   - `fitConversationToBudget` gates Rung (a) compaction on `estimateTokens(messages) >= 85_000` (`contextBudget.ts:901-907`), where `estimateTokens` is a naive `Math.ceil(chars / 4)` over `content`, `role`, `name`, and `JSON.stringify(tool_calls)` (`contextBudget.ts:232-246`).
   - On source code, JSON tool arguments, file paths, PowerShell commands, and unified diffs, local BPE tokenizers average **~3.0–3.5 chars/token** — undercounting actual tokens by **15–33%**.
   - In addition, `fitConversationToBudget` **does not count** `llmPayload.tools` schemas (`roundTools`, Layer 1 + host tools + git tools) or chat-template special tokens across hundreds of message turns.
   - As a result, actual engine `prompt_tokens` can climb to **`93.7K`** (or >`100K`) while `estimateTokens(conversationMessages)` is still `< 85,000`!
   - Worse, `fitContextWindow` (`contextBudget.ts:461-487`) reserves at most `2,500` tokens for tool schemas and `3,000–4,000` for artifact output headroom — **never reserving `ROUND_MAX_TOKENS` (`16,384`)**. When real prompt tokens exceed ~`114K` (still `< 100K` estimated under a 15%+ code undercount), `actualPromptTokens + 16,384` exceeds the `131,072` context window.

2. **Why only ONE compaction occurred across 308 rounds (`11.69M` prompt tokens total, `59K` final):**
   - `applyMicroElision` (`roundLoop.ts:705`, `microElision.ts:147-192`) runs _before_ `fitConversationToBudget` (`roundLoop.ts:711`), stubbing old tool results `>= 2000 chars` past the 5-result window.
   - This keeps per-round context **below `85,000` estimated tokens** for ~200 rounds, creating a long **40K–84K plateau** where every single round re-sends tens of thousands of tokens (`O(R^2)` cumulative prompt cost = `11.69M` tokens).
   - Once `estimateTokens` finally crosses `85,000` (at ~`93.7K` real tokens), Rung (a) compacts history down to `[system, digest, last 4 messages]`, and the remaining ~100 rounds climb back to **`59K`** without crossing `85,000` estimated tokens a second time.
   - And because `jobChunkingEnabled` was disabled in live `host-settings.json` (and broken when enabled — see E1/E4), `TOOL_ROUND_BACKSTOP = 1000` allowed the turn to run 308 rounds uninterrupted.

3. **Three un-elided growth sources that outrun micro-elision and push context past 85K:**
   - **Small tool results (`< 2000 chars`) are NEVER micro-elided (`microElision.ts:167`):** `host_replace_string` receipts, `git status`, short test outputs, `host_list_dir`, and error JSONs under 2,000 chars (~500–650 real tokens each) accumulate permanently across all 308 rounds.
   - **ALL `role === "assistant"` messages — including full `tool_calls` arguments — are NEVER micro-elided (`microElision.ts:156`):** Every `host_write_file`, `workspace_write_file`, `host_replace_string`, and `workspace_patch_file` call leaves its full file body / patch payload inside `assistant.tool_calls[].function.arguments` for the entire life of the turn until 85K triggers!
   - **Uncapped file reads (`roundLoop.ts:1695`, `host-bridge/server.ts:30,661`):** `workspace_read_file` and `host_read_file` deliberately bypass `clampToolOutput` (`isFileReadTool ? JSON.stringify(result) : clampToolOutput(...)`). A single unpaged `host_read_file` (up to `2 MB` = ~500K tokens!) or 5 large reads in `MICRO_ELISION_RECENT_WINDOW` can jump context past both `85K` and `100K` in a single round, forcing Rungs (b)/(c)/(d) destructive eviction.

4. **Mid-turn hybrid compaction (`0.65` escalation) is DEAD CODE for single-turn marathons (`roundLoop.ts:726-791`, `threadStore.ts:1583-1612`):**
   - First, `deploy/k8s/web-ui.yaml` does not set `COMPACTION_STRATEGY`, so `resolveCompactionStrategy()` defaults to `"extraction"` (`conversationCompaction.ts:100-107`).
   - Second, **even when `COMPACTION_STRATEGY=hybrid` IS set in cluster env**, `roundLoop.ts:727` calls `threadStore.compactThreadIncrementalHybrid(threadData, ...)`. During a single-turn 308-round board job, `threadData.messages` on disk contains only **2 messages** (`[user_brief, streaming_assistant_placeholder]`). `compactThreadIncrementalHybrid` checks `if (messages.length <= 4) return { noop: true, reason: "insufficient_messages" }` (`threadStore.ts:1585`)! So the hybrid rung ALWAYS no-ops mid-turn on single-turn jobs, falling back silently to `fitConversationToBudget`'s plain extraction digest!

5. **Mid-turn Rung (a) compaction evicts the sole `user` brief and injects a synthetic prompt (`conversationCompaction.ts:487,612-637`, `provider.ts:479-489`):**
   - On a 1-turn board job, `conversationMessages` is `[system, user (brief), assistant, tool, assistant, tool, ...]`.
   - When `compactConversationHistory` triggers at `85K`, `startIdx = 1` and `endIdx = messages.length - 4`, so `olderMessages = messages.slice(1, endIdx)` swallows index 1 (the **only** `user` message), truncates it to `2000 chars` inside `summarizeTurnHistory` (`conversationCompaction.ts:487`), and produces `[system, { role: "assistant", content: summary }, ...last4AssistantToolMsgs]`.
   - On the very next round, the `/v1/chat/completions` message normalizer (`provider.ts:442-489`) finds zero `role === "user"` messages and injects `{ role: "user", content: "Proceed with the request." }` — meaning long board briefs (>2,000 chars) lose their standing protocol, allowlists, and acceptance criteria after the first compaction!

### Blast Radius & Proposed Fix Shape (E5)

- **Blast radius:** Every long board turn pays `O(R^2)` prompt tokens (10M+ tokens, multi-hour prefill latency), risks silent context overflow near 131K when real tokens exceed the `chars/4` estimate, never uses hybrid compaction mid-turn, and loses long user briefs after its first compaction.
- **Proposed fix shape:**
  - `web-ui/lib/chat/roundLoop.ts` + `web-ui/lib/contextBudget.ts`: Calibrate compaction triggers using actual last-round `promptTokens` from the engine (`latestPromptTokens + estimateTokens(deltaSinceLastRound)`) alongside `estimateTokens`, include `roundTools` schema tokens in budget evaluation, and reserve `ROUND_MAX_TOKENS` headroom against `DEFAULT_CONTEXT_WINDOW_TOKENS` (or trigger proactive mid-turn compaction at a lower ceiling, e.g. 55–65% of budget or every N rounds when prompt > 40K, to bound the `O(R^2)` integral).
  - `web-ui/lib/microElision.ts`: Elide superseded `assistant.tool_calls` large write/patch argument bodies (replacing `content` / `newString` with byte-count + path stubs while preserving full args in `traces`) and apply a tighter size floor (e.g. `500 chars` once >15 rounds old) for superseded tool results.
  - `web-ui/lib/conversationCompaction.ts`: Always preserve the leading `role === "user"` message verbatim (or pin it outside `olderMessages` like `fitContextWindow` already does at `contextBudget.ts:504-507`), and wire mid-turn `hybrid` compaction in `roundLoop.ts:726` to run `runHybridCompaction(conversationMessages, ...)` on the live in-memory message array when `threadData.messages.length <= 4`.
  - **Proving tests:**
    1. Unit test in `web-ui/tests/hybridCompaction.test.ts`: single-turn job (`threadData.messages.length === 2`) with 50 in-flight tool rounds and `COMPACTION_STRATEGY=hybrid` invokes the hybrid summarizer rather than no-oping, and preserves the full leading `user` brief verbatim after compaction.
    2. Unit test in `web-ui/tests/microElision.test.ts`: superseded `host_write_file` / `workspace_write_file` tool-call argument payloads in older `assistant` messages are stubbed while recent window and `traces` remain intact.
    3. Unit test in `web-ui/tests/chatContextBudget.test.ts`: when engine `lastActualPromptTokens` exceeds `85K` while `estimateTokens` is `< 85K`, compaction still triggers on the next round.

## Checked and Found Sound (Negative Results)

The following components were inspected first-hand and confirmed sound at `6402579` — do not spend remediation effort refactoring them:

1. **Bounded SSE stream consumption (`web-ui/lib/board/streamTail.ts`: `readStreamTail`, `readResponseStreamTail`):** Maintains an exact `STREAM_TAIL_CAP_BYTES = 256 KiB` sliding tail buffer, tracks `totalBytes`, handles chunks exceeding cap size, aligns multi-byte UTF-8 boundaries (`(combined[startOffset] & 0xc0) === 0x80`), and releases the reader lock in `finally`. Eliminates full-stream OOM during marathon board turns.
2. **Token-economics aggregation leaf module (`web-ui/lib/tokenEconomics.ts`: `sumRoundPromptTokens`, `buildJobTokenRollup`, `computeThreadTokenEconomics`, `latestRoundPromptTokens`):** Pure, cycle-free, total-safe arithmetic that guards against `NaN`/`Infinity`/non-positive values and recomputes `thread.tokenEconomics` consistently on `saveThread` (`threadStore.ts:1083`). All E3 counting bugs live upstream in `roundLoop.ts` and `provider.ts`.
3. **Per-round wall-clock deadline primitive (`web-ui/lib/chat/turnEngine.ts`: `createRoundDeadline`):** Properly arms both inactivity (`180s`) and absolute total (`900s`) timers, unrefs both, aborts only `roundAbortController` (never `turnAbortController`), cleans up timers in `finally`, and reads env overrides dynamically per round (`contextBudget.ts:65-70`).
4. **Single-slot priority scheduler core (`web-ui/lib/slotScheduler.ts`: `PrioritySlotScheduler`):** Correctly enforces strict priority (`P0 > P1 > P2 > P3`), FIFO tie-breaking via monotonic `seq`, `AsyncLocalStorage` lease scoping, abort listener cleanup, and guaranteed `finally` release. (The priority inversion noted in F13 is in `chat/route.ts:454` hardcoding `P0_OWNER`, not in `PrioritySlotScheduler`.)
5. **Within-thread file read dedup (`web-ui/lib/readDedup.ts`: `ReadDedupRegistry`):** Deterministic SHA-256 content-hash dedup for `workspace_read_file` and `host_read_file` that re-anchors cleanly on file edits and preserves full payloads in `traces` + `readDedups` audit metadata.
6. **Per-job git worktree lock handling (`web-ui/lib/worktree.ts`: `createJobWorktree`, `removeJobWorktree`):** Bounds every `git` spawn to `30s` (`GIT_TIMEOUT_MS`), clears stale `.git/index.lock` and prunes worktrees across bounded retries (`GIT_LOCK_RETRIES = 3`), and removes ephemeral worktrees in `finally` (`chatTurnGate.ts:88-93`).
7. **Atomic thread persistence & cheap summary sweep (`web-ui/lib/threads/threadStore.ts`: `saveThread`, `listThreadSummaries`, `deletedThreadIds`):** Writes via temp-file + `renameSync` (preventing torn JSON on crash), caches summaries by `mtimeMs` so 60s sweeps avoid O(N) full-file JSON parsing, and tombstones deleted threads against late in-flight writes.

9. **Scheduler daemon drain re-entrancy & error isolation (`web-ui/lib/subagents/schedulerDaemon.ts`: `SchedulerDaemon.tick`, `boardDrainInFlight`):** Prevents overlapping board drains across 60s ticks and isolates per-schedule failures from aborting the tick loop.
10. **MCP session teardown & abandoned-stream close (`web-ui/lib/chat/roundLoop.ts:2320-2328`, `web-ui/lib/chat/turnEngine.ts:166-196`):** Closes every MCP client session in `finally` with isolated error handling and drains/closes `TransformStream` with a 1s timeout so abandoned HTTP clients cannot deadlock `JobQueue`.
